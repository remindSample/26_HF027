# Create Pull Request

현재 작업 브랜치의 커밋과 실제 코드 변경 사항을 분석하여 `develop` 브랜치로 향하는 GitHub Pull Request를 생성한다.

PR 제목과 본문은 실제 Git diff를 기반으로 한국어로 작성한다.

## 목적

사용자가 GitHub 웹사이트에 직접 접속하여 PR 제목과 내용을 작성하지 않아도 되도록 다음 작업을 자동으로 수행한다.

1. 현재 Git 저장소와 브랜치를 확인한다.
2. GitHub CLI 설치 및 로그인 상태를 확인한다.
3. 현재 브랜치의 변경 사항이 커밋되어 있는지 확인한다.
4. 현재 브랜치를 원격 저장소에 push한다.
5. `develop` 브랜치와 현재 브랜치의 차이를 분석한다.
6. 실제 변경 내용을 기반으로 PR 제목과 본문을 작성한다.
7. 기존 PR의 중복 여부를 확인한다.
8. GitHub Pull Request를 생성한다.
9. 생성된 PR 정보를 사용자에게 전달한다.

## 기본 설정

- 기본 base 브랜치는 `develop`이다.
- 현재 작업 브랜치를 head 브랜치로 사용한다.
- PR 제목과 본문은 한국어로 작성한다.
- PR 내용은 커밋 메시지만 복사하지 않고 실제 Git diff를 분석하여 작성한다.
- `main`, `master`, `develop` 브랜치에서는 PR을 생성하지 않는다.
- 사용자가 다른 base 브랜치를 명시한 경우에만 해당 브랜치를 사용한다.
- 사용자가 명시적으로 요청하지 않는 한 merge, rebase, reset, force push를 실행하지 않는다.
- PR 생성을 위해 코드나 설정 파일을 임의로 수정하지 않는다.
- 테스트를 실행하지 않았다면 실행했다고 작성하지 않는다.
- 실패한 작업을 성공했다고 보고하지 않는다.
- 기존에 열린 PR이 있다면 중복 PR을 생성하지 않는다.
- 현재 저장소 밖의 파일을 수정하지 않는다.
- 민감 정보, 토큰, 비밀번호, 환경 변수 값은 PR 본문에 포함하지 않는다.

## 명령 실행 규칙

- 명령은 현재 Git 저장소의 루트에서 실행한다.
- Windows PowerShell에서도 동작 가능한 명령을 우선 사용한다.
- PowerShell 실행 정책 문제를 피하기 위해 `npm.ps1`, `npx.ps1` 같은 PowerShell shim을 직접 사용하지 않는다.
- Node.js 관련 명령이 필요하면 `npm.cmd`, `npx.cmd`를 우선 사용한다.
- 명령 실패 시 같은 명령을 무의미하게 반복하지 않는다.
- 실패 원인을 먼저 확인하고 가능한 안전한 대체 명령을 한 번만 시도한다.
- 사용자 승인 없이 파괴적인 Git 명령을 실행하지 않는다.

금지되는 명령의 예시는 다음과 같다.

```sh
git reset --hard
git clean -fd
git push --force
git push --force-with-lease
git rebase
git merge
```

사용자가 명시적으로 요청하고 영향 범위를 이해한 경우가 아니라면 위 명령을 실행하지 않는다.

# 실행 절차

## 1. Git 저장소 확인

다음 명령을 실행한다.

```sh
git rev-parse --show-toplevel
```

명령이 실패하면 현재 위치가 Git 저장소가 아니므로 작업을 중단하고 사용자에게 알려준다.

저장소 루트 경로를 확인한 후 이후 명령은 해당 위치에서 실행한다.

## 2. GitHub CLI 확인

다음 명령으로 GitHub CLI 설치 여부를 확인한다.

```sh
gh --version
```

명령이 실패하면 PR을 생성하지 않고 다음 내용을 안내한다.

```text
GitHub CLI가 설치되어 있지 않아 PR을 생성할 수 없습니다.
GitHub CLI를 설치한 뒤 `gh auth login`으로 로그인해 주세요.
```

GitHub CLI가 설치되어 있다면 로그인 상태를 확인한다.

```sh
gh auth status
```

로그인되어 있지 않거나 인증이 만료된 경우 작업을 중단하고 다음 명령을 안내한다.

```sh
gh auth login
```

로그인을 대신 진행하려고 반복적으로 인증 명령을 실행하지 않는다.

## 3. 현재 브랜치 확인

다음 명령을 실행한다.

```sh
git branch --show-current
```

브랜치 이름이 비어 있으면 detached HEAD 상태이므로 PR을 생성하지 않는다.

현재 브랜치가 다음 중 하나이면 작업을 중단한다.

- `main`
- `master`
- `develop`

중단할 때 다음과 같이 설명한다.

```text
현재 브랜치에서는 PR을 생성할 수 없습니다.
기능 브랜치로 이동한 뒤 다시 실행해 주세요.
```

## 4. 원격 저장소 확인

다음 명령을 실행한다.

```sh
git remote -v
```

`origin` 원격 저장소가 없으면 작업을 중단한다.

GitHub 저장소 정보는 다음 명령으로 추가 확인할 수 있다.

```sh
gh repo view --json nameWithOwner,url,defaultBranchRef
```

저장소가 GitHub 저장소가 아니거나 현재 계정에 접근 권한이 없다면 PR을 생성하지 않는다.

## 5. 작업 디렉터리 상태 확인

다음 명령을 실행한다.

```sh
git status --short
```

출력 결과에 변경된 파일이 있다면 아직 커밋되지 않은 변경 사항이 존재한다는 뜻이다.

커밋되지 않은 변경 사항이 있을 경우:

- 파일을 자동으로 커밋하지 않는다.
- 파일을 자동으로 stage하지 않는다.
- 현재 커밋에 포함되지 않은 변경은 PR에 들어가지 않을 수 있음을 사용자에게 알린다.
- 사용자가 명시적으로 커밋까지 요청하지 않았다면 PR 생성을 중단한다.

안내 예시:

```text
아직 커밋되지 않은 변경 사항이 있어 PR 생성을 중단했습니다.
변경 사항을 커밋한 뒤 다시 실행해 주세요.
```

단, 추적되지 않는 파일이 PR과 관계없는 로컬 전용 파일임이 명확하고 사용자가 그대로 진행하도록 요청한 경우에는 계속할 수 있다.

## 6. base 브랜치 확인 및 원격 정보 갱신

기본 base 브랜치는 `develop`이다.

다음 명령으로 원격 `develop` 브랜치가 존재하는지 확인한다.

```sh
git ls-remote --exit-code --heads origin develop
```

원격 `develop` 브랜치가 없다면 PR을 생성하지 않고 사용자에게 알려준다.

원격 브랜치 정보를 갱신한다.

```sh
git fetch origin develop
```

fetch가 실패하면 PR을 생성하지 않는다.

## 7. 현재 브랜치의 커밋 존재 여부 확인

현재 브랜치와 `origin/develop` 사이에 커밋이 있는지 확인한다.

```sh
git log --oneline origin/develop..HEAD
```

출력이 비어 있다면 PR에 포함할 새 커밋이 없다는 의미이므로 작업을 중단한다.

안내 예시:

```text
현재 브랜치에 develop 브랜치보다 새로운 커밋이 없어 PR을 생성하지 않았습니다.
```

현재 브랜치가 `develop`보다 뒤처져 있더라도 자동으로 merge 또는 rebase하지 않는다.

필요하면 다음 명령으로 분기 상태를 확인한다.

```sh
git rev-list --left-right --count origin/develop...HEAD
```

충돌 가능성이 있거나 브랜치가 오래된 경우에도 PR 생성 자체가 가능한 상태라면 계속할 수 있지만, PR 본문의 참고 사항에 해당 내용을 기록한다.

## 8. 현재 브랜치 push

현재 브랜치의 upstream 설정 여부를 확인한다.

```sh
git rev-parse --abbrev-ref --symbolic-full-name @{upstream}
```

Windows PowerShell에서 `@{upstream}`이 해석 문제를 일으키면 다음처럼 따옴표를 사용한다.

```powershell
git rev-parse --abbrev-ref --symbolic-full-name '@{upstream}'
```

upstream이 설정되어 있지 않으면 다음 명령을 실행한다.

```sh
git push -u origin <현재 브랜치>
```

upstream이 이미 설정되어 있으면 다음 명령을 실행한다.

```sh
git push
```

push가 실패하면 PR을 생성하지 않는다.

다음과 같은 실패 원인을 구분하여 설명한다.

- 원격 브랜치에 다른 커밋이 있어 push가 거절됨
- 인증 또는 권한 부족
- 네트워크 오류
- 브랜치 보호 규칙
- 원격 저장소 주소 문제

push 실패 시 자동으로 force push하지 않는다.

## 9. 기존 PR 확인

현재 브랜치에서 `develop`로 향하는 열린 PR이 이미 있는지 확인한다.

우선 다음 명령을 사용한다.

```sh
gh pr list --state open --head <현재 브랜치> --base develop --json number,title,url,state,baseRefName,headRefName
```

열린 PR이 존재하면 새 PR을 생성하지 않는다.

기존 PR이 있을 경우 다음 정보를 사용자에게 전달한다.

- PR 번호
- PR 제목
- head 브랜치
- base 브랜치
- PR URL

예시:

```text
현재 브랜치에는 이미 열린 PR이 있습니다.

제목: feat: 보호자 회원가입 화면 구현
브랜치: feature/signup → develop
URL: https://github.com/...
```

닫히거나 merge된 과거 PR만 존재하는 경우에는 새 PR을 생성할 수 있다.

## 10. 변경 사항 수집

PR 제목과 본문을 작성하기 전에 다음 정보를 수집한다.

### 커밋 목록

```sh
git log --format="%h %s" origin/develop..HEAD
```

### 변경 파일 요약

```sh
git diff --stat origin/develop...HEAD
```

### 변경 파일 상태

```sh
git diff --name-status origin/develop...HEAD
```

### 전체 diff

```sh
git diff origin/develop...HEAD
```

### 필요 시 파일별 diff

전체 diff가 너무 큰 경우 변경 파일을 우선 분류한 뒤 중요한 파일을 개별 확인한다.

```sh
git diff origin/develop...HEAD -- <파일 경로>
```

다음 파일은 일반적으로 상세 분석 우선순위를 낮춘다.

- lock 파일
- 자동 생성 파일
- 빌드 결과물
- 캐시 파일
- 바이너리 파일
- 이미지 파일

단, 의존성 변경이나 설정 변경의 핵심 근거가 되는 경우에는 포함한다.

## 11. 변경 내용 분석 기준

실제 diff를 읽고 다음 항목을 분석한다.

- 새롭게 추가된 기능
- 기존 기능 수정
- 버그 수정
- UI 또는 스타일 변경
- 공통 컴포넌트 변경
- 라우팅 변경
- 상태 관리 변경
- API 요청 및 응답 구조 변경
- 타입 정의 변경
- 데이터 모델 변경
- 파일 또는 폴더 구조 변경
- 설정 파일 변경
- 의존성 변경
- 리팩터링
- 삭제된 기능 또는 코드
- 테스트 추가 또는 수정
- 문서 변경
- 사용자 화면 또는 동작에 미치는 영향
- 리뷰어가 확인해야 할 위험 요소
- 아직 완료되지 않은 부분
- 호환성 또는 마이그레이션 필요 여부

커밋 메시지와 실제 diff가 다르면 실제 diff를 기준으로 한다.

코드에서 명확하게 확인되지 않는 의도나 결과를 추측하지 않는다.

예를 들어 실제 테스트를 실행하지 않았다면 다음과 같이 작성한다.

```text
- 별도의 자동화 테스트는 실행하지 않음
```

다음처럼 작성하지 않는다.

```text
- 모든 테스트 통과
```

## 12. PR 유형 결정

변경의 핵심 성격에 따라 PR 제목의 type을 결정한다.

- `feat`: 새로운 기능 추가
- `fix`: 오류 또는 버그 수정
- `refactor`: 동작 변화가 크지 않은 코드 구조 개선
- `design`: UI, 스타일, 레이아웃 중심 변경
- `docs`: 문서 중심 변경
- `test`: 테스트 코드 중심 변경
- `chore`: 설정, 의존성, 빌드, 기타 유지보수
- `perf`: 성능 개선
- `ci`: CI/CD 설정 변경
- `revert`: 이전 변경 되돌리기

여러 유형이 섞여 있으면 사용자에게 가장 큰 영향을 주는 핵심 변경을 기준으로 하나를 선택한다.

## 13. PR 제목 작성

PR 제목 형식은 다음과 같다.

```text
<type>: <핵심 변경 내용>
```

제목 작성 규칙:

- 한국어로 작성한다.
- 가능하면 50자 이내로 작성한다.
- 변경의 핵심 결과가 드러나야 한다.
- 지나치게 넓거나 모호한 표현을 피한다.
- 파일명만 나열하지 않는다.
- 코드에서 확인할 수 없는 내용을 넣지 않는다.
- 마침표를 붙이지 않는다.
- 이슈 번호가 명확하게 제공된 경우에만 포함한다.

좋은 예시:

```text
feat: 보호자 회원가입 흐름 구현
fix: 헤더 타이틀 정렬 오류 수정
refactor: 공통 Header 컴포넌트 구조 개선
design: 게임 결과 화면 레이아웃 수정
chore: Expo 의존성 버전 업데이트
```

피해야 할 예시:

```text
수정
코드 변경
여러 가지 기능 추가
최종 수정본
작업 완료
```

## 14. PR 본문 작성

PR 본문은 다음 형식을 기본으로 사용한다.

```md
## 작업 내용

- 변경 사항 1
- 변경 사항 2

## 주요 변경 파일

- `파일 경로`: 변경 내용
- `파일 경로`: 변경 내용

## 확인 사항

- 리뷰어가 확인해야 할 내용

## 테스트

- 실행한 테스트 또는 검사
- 실행하지 않은 경우 그 사실과 이유

## 참고 사항

- 추가 전달 내용
- 없으면 `없음`
```

### 작업 내용 작성 규칙

- 실제 기능과 동작 변화를 중심으로 작성한다.
- 단순히 “수정했습니다”라고 쓰지 않는다.
- 무엇을 왜 또는 어떻게 변경했는지가 드러나게 작성한다.
- 지나치게 세부적인 코드 줄 단위 설명은 피한다.
- 관련 변경은 하나의 항목으로 묶는다.
- PR에 포함되지 않은 작업은 작성하지 않는다.

예시:

```md
## 작업 내용

- 보호자와 사용자 회원가입 진입 경로를 분리했습니다.
- 인증번호 입력 이후 비밀번호 설정 화면으로 이동하도록 회원가입 흐름을 연결했습니다.
- 회원가입 완료 후 로그인 화면으로 이동할 수 있도록 라우팅을 추가했습니다.
```

### 주요 변경 파일 작성 규칙

- 의미 있는 파일만 작성한다.
- 모든 파일을 기계적으로 나열하지 않는다.
- lock 파일은 중요한 의존성 변경이 있을 때만 작성한다.
- 각 파일이 어떤 역할로 변경되었는지 한 줄로 설명한다.

예시:

```md
## 주요 변경 파일

- `app/signup.tsx`: 사용자 유형 선택부터 가입 완료까지 회원가입 단계 구현
- `components/common/Header.tsx`: 회원가입 화면에서 사용할 공통 헤더 속성 확장
```

### 확인 사항 작성 규칙

리뷰어가 실제로 확인해야 할 내용을 작성한다.

예시:

```md
## 확인 사항

- 사용자와 보호자 버튼 선택 시 올바른 회원가입 흐름으로 진입하는지 확인이 필요합니다.
- 작은 화면에서도 입력창과 하단 버튼이 겹치지 않는지 확인이 필요합니다.
```

특별한 확인 사항이 없다면 다음과 같이 작성한다.

```md
## 확인 사항

- 변경된 화면의 기본 동작을 확인해 주세요.
```

### 테스트 작성 규칙

실제로 실행한 명령만 기록한다.

예시:

```md
## 테스트

- `npm.cmd run lint`
- Expo 개발 서버 실행 확인
```

테스트하지 않았다면 다음과 같이 작성한다.

```md
## 테스트

- 별도의 자동화 테스트는 실행하지 않음
```

테스트 실행이 PowerShell 정책 등의 이유로 실패했다면 사실 그대로 작성한다.

```md
## 테스트

- `npm.ps1` 실행 정책 문제로 실행하지 않고 `npm.cmd run lint`로 대체
- lint 검사 결과 오류 없음
```

`npm.cmd` 검사도 실패했다면 성공한 것처럼 작성하지 않는다.

### 참고 사항 작성 규칙

다음 내용을 필요한 경우 기록한다.

- 미완성 기능
- 추후 작업 필요 사항
- 기존 구조와의 호환성
- 브랜치가 develop보다 뒤처진 상태
- 환경별 확인 필요 사항
- 의존성 설치 필요 여부
- 데이터 마이그레이션 여부

특별한 내용이 없다면 다음과 같이 작성한다.

```md
## 참고 사항

PR 본문을 작성할 때 `references/pr-template.md`의 제목과 순서를 유지한다.

템플릿 안의 안내 문구는 실제 PR 본문에 포함하지 않고,
현재 브랜치의 실제 변경 사항으로 교체한다.

해당 내용이 없는 항목도 삭제하지 않는다.

- 확인 사항이 없으면 `없음`
- 테스트를 실행하지 않았으면 `별도의 자동화 테스트는 실행하지 않음`
- 참고 사항이 없으면 `없음`

## 15. 테스트 및 검사

변경 내용을 분석한 뒤 프로젝트에서 안전하게 실행 가능한 검사 명령을 확인한다.

`package.json`이 있는 JavaScript 또는 TypeScript 프로젝트라면 먼저 scripts를 확인한다.

```sh
git diff origin/develop...HEAD -- package.json
```

필요한 경우 `package.json` 내용을 읽고 다음 중 실제 존재하는 명령만 실행한다.

```powershell
npm.cmd run lint
npm.cmd run typecheck
npm.cmd test
```

규칙:

- 존재하지 않는 script를 추측하여 실행하지 않는다.
- 사용자가 요청하지 않은 장시간 빌드나 전체 테스트를 무조건 실행하지 않는다.
- PowerShell에서 `npm` 또는 `npx`가 `.ps1` 실행 정책으로 차단될 가능성이 있으면 처음부터 `npm.cmd`, `npx.cmd`를 사용한다.
- 같은 실행 정책 오류를 반복해서 재현하지 않는다.
- 테스트 실패가 코드 오류인지 환경 문제인지 구분한다.
- 테스트 실패가 있어도 사용자가 PR 생성을 요청했고 PR 생성이 가능한 경우에는 실패 내용을 PR 본문에 명시한 뒤 생성할 수 있다.
- 치명적인 오류 또는 커밋되지 않은 수정이 발생한 경우에는 PR 생성을 중단한다.
- 테스트 과정에서 파일이 변경되면 `git status --short`로 확인하고, 자동 생성 변경을 임의로 커밋하지 않는다.

## 16. PR 본문 임시 파일 생성

PR 본문은 명령줄 인수로 직접 길게 전달하지 않고 UTF-8 Markdown 임시 파일로 저장하는 것을 우선한다.

파일명 예시:

```text
.git/pr-body.md
```

또는 운영체제의 임시 폴더를 사용할 수 있다.

중요 규칙:

- UTF-8 인코딩으로 저장한다.
- PowerShell의 기본 인코딩으로 인해 한글이 깨지지 않도록 주의한다.
- 기존 소스 파일을 `Get-Content`와 `Set-Content`로 다시 저장하여 인코딩을 변경하지 않는다.
- 임시 파일만 새로 생성한다.
- 임시 파일을 프로젝트에 커밋하지 않는다.
- PR 생성 후 임시 파일은 삭제할 수 있다.

PowerShell을 사용할 경우 UTF-8 인코딩을 명시한다.

```powershell
[System.IO.File]::WriteAllText(
  ".git/pr-body.md",
  $prBody,
  [System.Text.UTF8Encoding]::new($false)
)
```

셸 heredoc을 사용할 수 있는 환경이라면 해당 방식을 사용할 수 있다.

## 17. PR 생성

다음 명령을 사용한다.

```sh
gh pr create --base develop --head <현재 브랜치> --title "<생성한 PR 제목>" --body-file ".git/pr-body.md"
```

사용자가 다른 base 브랜치를 명시했다면 `develop` 대신 해당 브랜치를 사용한다.

PR 생성 전 마지막으로 다음 사항을 확인한다.

- 현재 브랜치가 기능 브랜치인지
- base 브랜치가 올바른지
- 현재 브랜치가 push되었는지
- 열린 중복 PR이 없는지
- PR 제목이 실제 변경을 반영하는지
- PR 본문이 실제 diff를 반영하는지
- 테스트 결과를 과장하지 않았는지
- 민감 정보가 포함되지 않았는지

PR 생성 명령이 실패하면 오류 메시지를 확인하여 원인을 설명한다.

자동으로 여러 번 PR 생성을 반복하지 않는다.

## 18. PR 생성 결과 검증

PR 생성 후 다음 명령으로 결과를 확인한다.

```sh
gh pr view --json number,title,body,url,state,baseRefName,headRefName
```

다음을 검증한다.

- PR 상태가 `OPEN`인지
- base 브랜치가 `develop` 또는 사용자가 지정한 브랜치인지
- head 브랜치가 현재 브랜치인지
- 제목이 정상적으로 등록되었는지
- 본문이 정상적으로 등록되었는지
- PR URL이 존재하는지

검증에 실패하면 PR이 완전히 생성되었다고 단정하지 않는다.

## 19. 임시 파일 정리

PR 생성에 사용한 임시 파일이 `.git` 내부에 있다면 삭제할 수 있다.

PowerShell 예시:

```powershell
Remove-Item ".git/pr-body.md" -ErrorAction SilentlyContinue
```

임시 파일 삭제 실패는 PR 생성 성공 여부에 영향을 주지 않지만 사용자에게 불필요하게 과장하여 보고하지 않는다.

## 20. 최종 결과 보고

성공한 경우 다음 형식으로 사용자에게 알려준다.

```text
PR을 생성했습니다.

제목: <PR 제목>
브랜치: <현재 브랜치> → develop
테스트: <실행한 검사 요약>
URL: <PR URL>
```

예시:

```text
PR을 생성했습니다.

제목: feat: 보호자 회원가입 흐름 구현
브랜치: feature/signup → develop
테스트: npm.cmd run lint 통과
URL: https://github.com/example/repository/pull/12
```

기존 PR이 있었던 경우 다음 형식으로 알려준다.

```text
새 PR은 생성하지 않았습니다. 현재 브랜치에 이미 열린 PR이 있습니다.

제목: <기존 PR 제목>
브랜치: <현재 브랜치> → develop
URL: <기존 PR URL>
```

실패한 경우 다음 정보를 포함한다.

- 실패한 단계
- 확인된 오류 원인
- 사용자가 수행해야 할 다음 작업

예시:

```text
PR을 생성하지 못했습니다.

실패 단계: 현재 브랜치 push
원인: 원격 브랜치에 로컬에 없는 커밋이 있어 push가 거절되었습니다.
다음 작업: 원격 변경 사항을 확인한 뒤 merge 또는 rebase 방법을 결정해야 합니다.
```

# 예외 처리

## 현재 브랜치에 커밋이 없는 경우

PR을 생성하지 않는다.

```text
develop 브랜치와 비교했을 때 새로운 커밋이 없습니다.
```

## 커밋되지 않은 변경이 있는 경우

자동 커밋하지 않고 중단한다.

```text
커밋되지 않은 변경 사항이 있어 PR 생성을 중단했습니다.
변경 사항을 확인하고 커밋한 뒤 다시 실행해 주세요.
```

## GitHub CLI가 없는 경우

```text
GitHub CLI가 설치되어 있지 않아 PR을 생성할 수 없습니다.
GitHub CLI 설치 후 `gh auth login`을 실행해 주세요.
```

## GitHub 로그인이 필요한 경우

```text
GitHub CLI 인증이 필요합니다.
터미널에서 `gh auth login`을 실행한 뒤 다시 요청해 주세요.
```

## push가 거절된 경우

force push하지 않는다.

```text
원격 브랜치와 로컬 브랜치의 이력이 달라 push가 거절되었습니다.
원격 변경 사항을 확인한 뒤 안전한 동기화 방법을 결정해야 합니다.
```

## 이미 열린 PR이 있는 경우

새 PR을 생성하지 않고 기존 PR 링크를 반환한다.

## 변경 파일이 너무 많은 경우

- 파일 목록과 diff stat을 먼저 분석한다.
- 핵심 기능 파일을 우선 확인한다.
- 자동 생성 파일과 lock 파일은 별도로 분리한다.
- 분석하지 못한 부분을 분석한 것처럼 작성하지 않는다.
- 필요한 경우 PR 본문 참고 사항에 변경 범위가 크다는 점을 기록한다.

## 바이너리 파일이 포함된 경우

이미지, 폰트, 영상 등 바이너리 파일은 내용 diff를 직접 분석할 수 없으므로 파일 추가·삭제·교체 여부만 기록한다.

예시:

```text
- 로그인 화면에서 사용하는 로고 이미지 파일을 교체했습니다.
```

이미지의 시각적 변화 내용을 확인하지 못했다면 구체적인 디자인 변화는 추측하지 않는다.

# 보안 규칙

다음 내용은 PR 제목, 본문, 로그 요약에 포함하지 않는다.

- GitHub 토큰
- API 키
- 비밀번호
- `.env` 파일의 실제 값
- 개인 인증 정보
- 세션 쿠키
- 비공개 서버 주소
- 개인정보

diff에서 민감 정보가 발견되면 PR 생성을 중단하고 사용자에게 해당 파일을 확인하도록 알린다.

민감 정보가 포함될 가능성이 높은 파일 예시:

- `.env`
- `.env.local`
- `.env.production`
- 인증서 파일
- 개인 키 파일
- 서비스 계정 키
- 토큰이 포함된 설정 파일

# 사용자 요청 해석

다음과 같은 요청을 받으면 이 skill을 사용할 수 있다.

```text
PR 올려줘
현재 브랜치 PR 만들어줘
develop으로 풀 리퀘스트 생성해줘
push하고 PR까지 만들어줘
변경 내용 분석해서 PR 작성해줘
깃허브에 PR 등록해줘
```

사용자가 단순히 PR 본문 초안만 요청한 경우에는 실제 `gh pr create`를 실행하지 않고 제목과 본문만 작성한다.

사용자가 PR 생성 전 내용을 검토하고 싶다고 명시한 경우에는:

1. 변경 사항을 분석한다.
2. PR 제목과 본문 초안을 보여준다.
3. 사용자의 명시적인 생성 요청이 있을 때만 PR을 생성한다.

사용자가 바로 생성해 달라고 요청한 경우에는 필요한 안전 점검 후 별도 확인 없이 PR을 생성할 수 있다.

# 완료 조건

다음 조건을 모두 만족해야 작업이 완료된 것으로 판단한다.

- GitHub CLI 인증 상태 확인
- 올바른 Git 저장소 확인
- 기능 브랜치 확인
- 커밋되지 않은 변경 여부 확인
- `develop`과의 차이 확인
- 현재 브랜치 push 완료
- 중복 PR 여부 확인
- 실제 diff 기반 PR 제목 작성
- 실제 diff 기반 PR 본문 작성
- PR 생성 명령 성공
- 생성된 PR 정보 검증
- PR URL 사용자에게 전달

위 조건 중 하나라도 실패하면 완료되었다고 보고하지 않는다.
