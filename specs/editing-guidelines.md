# 파일 수정 작업 지침

## 목적

파일 수정 과정에서 발생할 수 있는 한글 인코딩 손상과 불필요한 코드 변경을 방지한다.

특히 다음 두 가지 문제를 예방하는 것을 목적으로 한다.

1. PowerShell을 통한 파일 저장 과정에서 한글 문자열이 깨지는 문제
2. 사용자가 요청한 부분 외의 코드까지 임의로 수정되는 문제

---

## 1. 파일 인코딩 유지

### 문제

한글이 포함된 UTF-8 파일을 PowerShell의 `Get-Content`로 읽고 `Set-Content`로 다시 저장할 경우, 기존 파일의 인코딩이 변경될 수 있다.

Windows PowerShell 5 계열에서는 `Set-Content`의 기본 저장 인코딩이 UTF-8로 보장되지 않는다. 이 때문에 파일의 한글 문자열이 잘못된 바이트 형식으로 저장되어 다음과 같은 깨진 문자열이 발생할 수 있다.

```text
吏덈Ц
筌욌뜄揆
```

이는 코드 로직의 문제가 아니라, 파일을 다시 저장하는 과정에서 UTF-8 인코딩이 유지되지 않아 발생하는 문제다.

### 수정 원칙

한글이 포함된 파일을 수정할 때는 다음 원칙을 따른다.

1. 파일 수정에는 `apply_patch`를 우선 사용한다.
2. 단순 문자열 교체를 위해 `Get-Content`와 `Set-Content`를 조합하지 않는다.
3. PowerShell로 파일 전체를 다시 저장해야 할 경우 UTF-8 인코딩을 명시한다.
4. 기존 파일의 줄바꿈 형식과 인코딩을 가능한 한 유지한다.
5. 수정 후 한글 문자열이 정상적으로 보이는지 반드시 확인한다.

### PowerShell 저장 예시

PowerShell을 사용해야 하는 경우 다음과 같이 UTF-8을 명시한다.

```powershell
$content = [System.IO.File]::ReadAllText($filePath)

[System.IO.File]::WriteAllText(
    $filePath,
    $content,
    [System.Text.UTF8Encoding]::new($false)
)
```

`UTF8Encoding(false)`는 BOM이 없는 UTF-8 형식으로 파일을 저장한다.

### 금지 예시

다음과 같은 방식은 한글 파일의 인코딩을 변경할 수 있으므로 사용하지 않는다.

```powershell
Get-Content $filePath | Set-Content $filePath
```

```powershell
$content = Get-Content $filePath
Set-Content $filePath $content
```

## 2. 요청 범위 외 수정 금지

### 문제

파일의 특정 부분만 수정하도록 요청했음에도 다음과 같은 불필요한 변경이 함께 발생할 수 있다.

* 요청하지 않은 코드의 구조 변경
* 변수명 또는 함수명 변경
* 주석 삭제 또는 수정
* 코드 정렬 및 포맷 변경
* import 순서 변경
* 기존 로직 리팩터링
* 문자열 표현 방식 변경
* 파일 전체 재작성

이러한 변경은 코드 충돌을 발생시키거나 기존 기능에 예상하지 못한 영향을 줄 수 있다.

### 수정 원칙

파일을 수정할 때는 사용자가 명시한 범위만 변경한다.

1. 요청받은 코드 블록 또는 기능만 수정한다.
2. 요청과 직접 관련 없는 코드는 변경하지 않는다.
3. 코드 품질 개선이나 리팩터링이 가능하더라도 임의로 적용하지 않는다.
4. 포맷팅은 수정한 줄에 필요한 최소 범위로 제한한다.
5. 파일 전체를 새 내용으로 덮어쓰지 않고 부분 패치를 사용한다.
6. 기존 주석, 네이밍, 코드 스타일을 유지한다.
7. 수정이 다른 부분에 영향을 줄 수 있다면 먼저 영향 범위를 설명한다.
8. 추가로 개선할 부분을 발견하더라도 요청한 작업과 함께 임의로 수정하지 않는다.
9. 개선이 필요하다고 판단한 내용은 우선 사용자가 요청한 작업을 완료한 후 별도의 제안으로 안내한다.
10. 추가 개선 사항을 제안할 때는 현재 작업에 포함하여 수정한 내용과 아직 적용하지 않은 제안을 명확히 구분한다.
11. 사용자가 추가 개선을 요청한 경우에만 해당 내용을 실제 파일에 반영한다.


### 허용되는 수정

다음과 같이 요청을 수행하기 위해 반드시 필요한 변경은 허용된다.

* 새로 사용하는 모듈의 import 추가
* 타입 오류 해결을 위한 관련 타입 수정
* 변경한 함수가 정상 동작하기 위한 직접적인 호출부 수정
* 문법 오류를 방지하기 위한 최소한의 수정

단, 이 경우에도 변경 범위는 최소화해야 한다.

### 허용되지 않는 수정

다음 변경은 별도의 요청이 없는 한 수행하지 않는다.

* 전체 컴포넌트 구조 재설계
* 관련 없는 함수의 리팩터링
* 기존 UI 스타일 변경
* 불필요한 변수명 변경
* 전체 파일 자동 포맷팅
* 기존 주석 제거
* 파일 또는 폴더 이름 변경
* 사용하지 않는 코드라는 이유로 임의 삭제

## 3. 파일 수정 절차

파일 수정 작업은 다음 순서로 진행한다.

### 1단계: 요청 범위 확인

사용자가 요청한 파일, 기능, 코드 영역을 확인한다.

수정 전 다음 내용을 구분한다.

* 반드시 변경해야 하는 부분
* 변경하면 안 되는 부분
* 변경이 필요할 가능성이 있는 연관 부분

### 2단계: 기존 코드 확인

수정 대상 주변 코드를 확인해 기존 구조와 스타일을 파악한다.

파일 전체를 재작성하지 않고 필요한 문맥만 읽는다.

### 3단계: 최소 범위 수정

가능한 경우 `apply_patch`를 사용하여 필요한 줄만 수정한다.

패치에는 요청과 관련된 변경만 포함한다.

### 4단계: 변경 사항 검토

수정 후 다음 내용을 확인한다.

* 요청한 기능이 반영되었는가
* 요청하지 않은 코드가 변경되지 않았는가
* 한글 문자열이 깨지지 않았는가
* 기존 코드 스타일이 유지되었는가
* import, 타입, 문법 오류가 발생하지 않았는가

### 5단계: 변경 범위 보고

수정 결과를 설명할 때 실제로 변경한 부분만 명확히 안내한다.

요청하지 않은 추가 개선 사항이 있다면 코드에 반영하지 않고 별도의 제안으로만 전달한다.

---

## 4. 변경 최소화 기준

수정 전후의 차이는 가능한 한 작아야 한다.

좋은 수정은 다음 조건을 만족한다.

* 변경된 줄 수가 요청 범위에 비례한다.
* 기존 코드와 동일한 작성 방식을 유지한다.
* 관련 없는 공백 및 줄바꿈 변경이 없다.
* 기존 파일 인코딩을 유지한다.
* 코드 리뷰 시 변경 목적을 쉽게 파악할 수 있다.

예를 들어 버튼 문구 하나를 변경하는 요청이라면 버튼 문구가 있는 한 줄만 수정해야 한다.

```diff
- <Text>로그인하기</Text>
+ <Text>로그인</Text>
```

다음과 같이 컴포넌트 전체를 다시 작성해서는 안 된다.

```diff
- 기존 컴포넌트 전체
+ 새롭게 재작성된 컴포넌트 전체
```

---

## 5. 예외 상황

요청한 부분만 수정해서는 기능을 구현할 수 없는 경우, 필요한 추가 변경 사항을 명확히 구분한다.

예시:

```text
요청한 버튼 동작을 구현하려면 현재 파일의 버튼 코드 외에도
라우팅 import와 이벤트 핸들러 추가가 필요합니다.
기존 UI와 다른 로직은 변경하지 않습니다.
```

추가 수정이 필요한 경우에도 다음 조건을 지킨다.

* 요청 기능과 직접적으로 연결된 부분만 수정한다.
* 수정 이유를 설명한다.
* 기존 동작을 최대한 유지한다.
* 불필요한 구조 변경은 하지 않는다.

---

## 핵심 규칙

> 한글이 포함된 파일은 UTF-8 인코딩을 유지하며, `apply_patch`를 우선 사용한다.

> 사용자가 지정한 수정 범위 외의 코드는 임의로 변경하지 않는다.

> 파일 전체 재작성보다 최소 단위의 부분 수정을 우선한다.

> 추가 개선이 필요하더라도 요청받지 않은 변경은 코드에 직접 적용하지 않는다.

> 추가 개선 사항이 있더라도 임의로 반영하지 않고, 요청받은 작업을 먼저 완료한 후 별도로 제안한다.
